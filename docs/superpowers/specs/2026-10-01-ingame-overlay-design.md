# 게임 안 오버레이 창 설계

- 작성일: 2026-10-01
- 근거: `analysis/findings.md` "게임 안 오버레이 창 — DX12 후킹 + Dear ImGui (2026-10-01, 스파이크)"
- 상태: 승인됨(2026-10-01)
- 구현 계획: 계획 A `docs/superpowers/plans/2026-10-01-ingame-overlay-plan-a.md`(8절의 1~3단계). 계획 B(4~7단계)는 계획 A를 끝낸 뒤 쓴다.
- 계획을 쓰며 고친 곳(2026-10-01): 3.2 파일 목록, 3.3 입력 처리 방식(큐 대신 재진입 잠금, 기본 IME 처리 끄기), 4.2 밖에서 고친 `overlay.json` 다시 읽기, 5.2 입력 예외, 6 도구

## 1. 목적과 범위

### 1.1 목적
지금은 설정을 바꾸려면 게임 밖의 패널(`MLToybox.Panel.exe`)을 따로 켜야 한다. 패널의 기능을 게임 화면 안의 창으로 옮겨, 게임을 보면서 바로 설정하게 한다.

### 1.2 사용자가 정한 것
- 방식: 게임 화면 위 오버레이(DX12 후킹 + Dear ImGui).
- 범위: 패널의 탭 전부.
- 패널: 오버레이로 대체한다. 패널 코드는 비상용으로 남겨 두고 더 고치지 않는다.
- 반영: 값을 바꾸면 즉시 반영한다("적용" 버튼 없음).
- 구조: 별도 DLL + 공용 코어(접근 A).
- 용병단: 개수 제한 없이 등록하고, "사용" 체크는 최대 3개, 체크한 것만 고용 창에 올린다.

### 1.3 요구사항
| # | 요구사항 |
|---|---|
| R1 | 게임 화면 안의 창에서 패널의 8개 탭(자원, 영주, 건설, 업그레이드, 군사, 용병, 인구, 상태) 기능을 모두 쓸 수 있다 |
| R2 | 키 하나로 창을 열고 닫는다. 기본은 Insert이고 바꿀 수 있다 |
| R3 | 값을 바꾸면 2.3절의 규칙대로 즉시 `control.json`에 저장된다 |
| R4 | 마우스가 창 위에 있거나 입력 칸에 커서가 있을 때의 입력은 게임에 넘기지 않는다. 그 밖의 입력은 게임이 평소대로 받는다 |
| R5 | 오버레이가 실패해도 게임을 튕기게 하지 않는다. 기존 Lua 기능, 기존 네이티브 기능, 패널은 오버레이 없이도 동작한다 |
| R6 | 브리지 프로토콜(`control.json` version 1, `status.json`)의 모양을 바꾸지 않는다. 추가는 `status.overlay` 하나다 |
| R7 | 용병단은 개수 제한 없이 등록한다. "사용"은 최대 3개이고, 사용 중인 것만 고용 창에 올라간다. 체크를 끄면 목록에서 빠진다 |
| R8 | 패널(`panel/`) 코드는 바꾸지 않는다 |

### 1.4 범위 밖
- 패널을 레포에서 빼는 일(오버레이를 충분히 써 본 뒤 따로 결정).
- 게임패드 조작, 다국어, 색 테마 선택.
- 프레임 생성(FSR·DLSS FG)을 켠 상태에서의 동작 보장. 튕기지 않게만 한다(5절).
- Lua 기능 모듈의 동작 변경. Lua는 오버레이 DLL을 올리고 상태를 합치는 것만 바뀐다.
- 게임을 멈추거나 게임 UI와 모양을 맞추는 일.

## 2. 화면과 동작

### 2.1 창
- 창은 하나다. 제목은 "MLToybox". 끌어서 옮기고 크기를 바꿀 수 있다.
- 처음 크기는 640×720, 위치는 화면 왼쪽 위(80, 80)다. 위치와 크기는 `overlay.json`에 저장해 다음 실행 때 되살린다. 해상도가 줄어 창이 화면 밖에 있으면 화면 안으로 옮긴다.
- 게임을 켜면 닫힌 상태로 시작한다. 처음 그리기 시작한 뒤 8초 동안 화면 왼쪽 위에 "Insert: MLToybox" 안내를 띄운다(키 이름은 설정을 따른다).
  - 맵에 들어갈 때마다(상태가 메인 메뉴에서 게임 안으로 바뀔 때) 다시 8초 동안 띄운다. 모드와의 연결이 끊겼다 돌아온 것은 맵에 들어간 것으로 치지 않는다. 처음 안내는 메인 메뉴가 나오기 전의 검은 시작 화면에 떠서 보기 어려웠다(계획 A 구현 검증).
- 글꼴은 맑은 고딕(`C:\Windows\Fonts\malgun.ttf`, 한글 범위) 18px에 배율을 곱한 크기다. 글꼴 파일을 못 읽으면 ImGui 기본 글꼴로 뜨고(한글은 깨진다) 상태 파일에 적는다.
- 창이 닫혀 있고 안내도 없으면 ImGui 프레임을 만들지 않는다.

### 2.2 상태 줄
창 맨 위 한 줄. 패널 하단의 표시와 같은 뜻이다.

| 표시 | 조건 |
|---|---|
| ● 적용됨 | 게임 안이고 `status.appliedSeq >= 마지막으로 보낸 seq` |
| ● 적용 대기 중 | 게임 안이고 아직 적용되지 않음 |
| ● 메인 메뉴 | `status.inGame == false` |
| ● 모드 응답 없음 | `status.json`이 없거나 `heartbeat`가 5초 넘게 지남 |
| ● 저장 실패 | `control.json` 저장이 실패한 상태(다시 시도 중) |

### 2.3 즉시 반영 규칙
| 종류 | 반영 시점 |
|---|---|
| 체크박스, 목록 선택 | 바꾸는 즉시 |
| 숫자 칸, 자원 목표 표의 칸 | Enter를 누르거나 포커스가 떠날 때. 값이 바뀌었을 때만 |
| 용병단 편집(이름, 구성, 고용비, 도착 영지, 깃발) | "등록"을 누를 때. 검증에 실패하면 반영하지 않고 이유를 표시한다 |
| 용병단 "사용" 체크, 삭제 | 즉시 |
| 일회성 버튼(분대 생성, 재구성, 꾸미기 열기, 가족 추가, 지금 설정) | 누르는 즉시 명령을 보낸다 |

- "적용"·"되돌리기" 버튼은 없다.
- 숫자 칸은 전각 숫자(０-９), 공백, 쉼표를 허용한다(패널의 `NumberInput`과 같은 규칙). 해석할 수 없는 입력은 버리고 이전 값을 유지한다.

### 2.4 탭
탭은 8개다: 자원, 영주, 건설, 군사, 용병, 인구, 상태, 로그. "로그"는 오버레이에만 있다(2026-10-02 사용자 요청). 패널의 8개 탭 가운데 "업그레이드"는 건설 탭에 합쳤다(2026-10-02 사용자 결정. 건물 업그레이드 표 `DT_Upgrades`와 주거지 레벨 조건을 고치는 건물 기능이기 때문이다). 설정 파일의 모양은 그대로다(`features.upgrade`). 문구는 패널과 같게 한다. 아래에서 "…"로 줄인 문구는 `panel/MLToybox.Panel/MainForm.cs`와 `MercenaryTab.cs`에 있는 문구 전체를 쓴다. 패널에만 있는 "게임 경로 변경"은 없다.

**자원**
- "자원 목표값 유지" 체크, "주기(초)"(1~60), "모두 이 값으로"(값 0~1,000,000과 버튼), "영지" 선택.
- 영지 선택: "공통 (모든 내 영지, 현재=합계)"과 `status.regions`의 영지들(`이름 (키)`).
- 표: 자원 / 분류 / 현재 / 목표. 목표 칸이 비면 관리하지 않는다. 영지를 고르면 목표 열 제목이 "영지 목표"가 되고 국고·영향력(`Treasury`, `Influence`) 행을 숨긴다. 표 위에 한 줄로 "목표 빈칸 = 관리 안 함(영지: 공통 목표를 따름) · 헤더를 누르면 정렬 · 열 경계를 끌면 너비 조정"을 보인다.
- 행은 `status.resourceIds`와 현재 값이 있는 자원을 합쳐 만든다. 모드가 목록을 알려 주지 않았을 때(게임 밖)는 목표의 키로 만든다. 목표만 남아 있고 목록에 없는 자원(게임이 더 쓰지 않아 모드가 뺀 품목)은 줄로 보이지 않고, 설정에서는 지우지 않는다(패널의 `ResourceRows.Build`는 목표의 키도 합친다. 2026-10-02에 자원 목록을 게임의 품목 표에 맞추며 달리했다).
- 이름과 분류(2026-10-02 사용자 요청): 모드가 시작할 때 쓰는 이름 표(`bridge/catalog.json`, 4.6)에서 자원의 한글 이름, 분류(건설, 식량, 제작 재료, 일용품, 군사), 묶음(고기, 채소 …), 게임의 순서를 읽는다. "자원" 열은 한글 이름(마우스를 올리면 내부 이름), "분류" 열은 "식량 · 고기" 꼴이다. 이름 표에 없는 자원은 내부 이름으로, 분류 "기타"로, 맨 뒤에 보인다. 이름 표를 읽지 못하면 모든 줄이 그렇게 보인다.
- 정렬: 헤더를 누르면 그 열로 정렬하고 다시 누르면 방향이 바뀐다. 처음에는 "분류" 오름차순(게임의 영지 창 순서)이다. 현재·목표는 처음 누를 때 큰 값부터다. 값이 없는 줄(현재 "-", 목표 빈칸)은 어느 방향에서도 뒤에 둔다. 같은 값끼리는 게임의 순서다.
  - 정렬한 순서는 기억해 둔다. 정렬 열·방향, 영지, 분류, 검색어, 줄의 구성이 바뀔 때만 다시 정렬한다. 현재 값이나 목표가 바뀔 때마다 줄이 옮겨 가면 누르려던 칸이 달아나기 때문이다.
- 열 너비: 열 경계를 끌어 바꾼다. 끌기를 끝내면 열 너비를 표 너비에 대한 백분율로 `overlay.json`의 `resourceColumns`에 적고, 다음 실행에 그 너비로 연다. 창 크기를 바꾸는 것은 열 너비를 바꾼 것으로 보지 않는다.
- 분류 고르기: "전체"와 지금 줄들에 있는 분류. 고르면 그 분류의 줄만 보인다. 골라 둔 분류가 없어지면 "전체"로 돌아간다.
- 검색: 글자 칸(한글 조합 가능, 2.5)과 한/영 단추, "지우기". 이름, 내부 이름, 분류, 묶음에 그 글이 들어 있는 줄만 보인다(앞뒤 공백을 빼고, 영문 대소문자를 가리지 않는다). 옆에 "보이는 줄 수 / 전체 줄 수"를 보인다.
- "모두 이 값으로"는 지금 보이는 범위의 모든 행 목표를 그 값으로 채우고 저장한다. 분류나 검색으로 줄을 추렸으면 보이는 줄에만 적용하고, 단추 글이 "보이는 N줄을 이 값으로"가 된다.
- 영지 목표가 하나도 없으면 그 영지 키를 `regionTargets`에서 지운다(패널의 `ResourceScope.Store`).

**영주**
- "영주 자원 목표값 유지 (영지와 무관한 전체 값)" 체크.
- 국고, 영향력, 왕의 총애 각각: 체크, 목표(0~10,000,000), "지금 설정", "현재: N".
- 체크를 끄면 그 키를 설정에서 뺀다(관리 안 함). "지금 설정"은 `setLord` 명령을 보낸다.
- 설명 두 줄(패널과 같은 문구).

**건설**: "건설 기능 사용", "배치 제한 무시 (영지 경계 안, 네이티브 DLL)", "즉시 완공 (네이티브 DLL)", "즉시 수리", "자재 불필요 (건설 자재 없이 공사)", "지역당 개수 제한 해제 (…)".

**업그레이드**(건설 탭 안, "업그레이드" 구분선 아래): "업그레이드 조건·비용·해금 무시". "건설 기능 사용"과 따로 켜고 끈다.

**군사**
- "군사 기능 사용", "민병대 장비 요구 무시", "징집 조건(집 레벨·훈련) 무시 — …", "민병대 모집비 0", "부대 수 상한 해제".
- 병력 생성: 병종(13종), 개수(1~5), 위치(`status.playerRegions`. 없으면 "내 첫 영지"), "분대 생성" → `spawnSquads`.
- 재구성: "해제된 생성 분대: N개 (병종별)"과 "재구성" 버튼(`disbanded > 0`이고 `pending == 0`일 때만) → `reformSquads`.
- 수행원 꾸미기: 분대 선택(`status.retinue.squads`, `#63 친위대 - 1단계 ×36 (생성)` 형식)과 "꾸미기 열기"(`editing`이 있으면 "꾸미기 열림 (#id)"로 바뀌고 눌리지 않음) → `customizeRetinue`. 위치는 위의 "위치" 영지를 쓴다.
  - 명령을 보낸 뒤에는 오버레이 창을 닫는다(게임의 꾸미기 화면을 가리지 않게).

**용병** (R7)
- "용병 기능 사용 (고용 창 자동 보충)", "내 용병단 고용비 환급, 유지비 0", "커스텀 용병단 AI 잠금 (고용 창을 열 때만 설정한 고용비)".
- 표: 사용 / 이름 / 구성 / 고용비 / 도착 영지 / 깃발. 줄 어디를 눌러도 편집 영역에 실린다("사용" 체크는 따로 눌린다).
- 설정 파일의 용병단에 `enabled` 키가 없으면 "사용"으로 본다(패널, 오버레이, 모드가 모두 같다). 항목 안의 모르는 키는 그 용병단을 고쳐 써도 남긴다(이름으로 찾는다).
- 등록한 용병단의 수에는 제한이 없다. "사용" 체크는 최대 3개다. 네 번째를 켜려 하면 켜지지 않고 "사용은 최대 3개입니다."를 표시한다.
- "새 용병단", "삭제".
- 편집: 이름(최대 40자), 분대 추가(병종, 개수, "추가"), 구성 목록과 "선택 병종 빼기", "합계 N / 10", 고용비(0~10,000,000), 도착 영지("내 첫 영지" + 내 영지 + 저장돼 있지만 목록에 없는 키), 깃발("칸의 것 그대로" + 순정 용병단 11개), "등록".
- 새로 등록할 때 사용 중인 것이 이미 3개면 "사용"을 끈 채로 등록하고 그렇게 알린다.
- 편집 중에 목록이 밖에서(패널, 손 편집) 바뀌면 편집하던 용병단을 실었던 내용으로 다시 찾는다. 없어졌거나 내용이 바뀌었으면 편집 대상에서 풀고 알린다(자리 번호만 믿으면 "삭제"·"등록"이 다른 용병단에 적용된다).
- 검증 규칙과 오류 문구는 패널의 `MercCompanyRules`와 같다(3.4절).
- 상태 줄: "고용 창: …", "고용 중: 내 용병단 N개, AI N개 · 맵을 불러온 뒤 환급 N", "띄우지 못함: 이름 — 이유", "참고: …".

**인구**
- "인구 기능 사용", "영지" 선택("공통 (모든 내 영지)" + `status.population.regions`), "자연 이민 배율(배)"(1~10).
- 목표 가족 수(0~1000): 공통이면 "영지마다 최소 가족 수(0 = 끔, 부족분만 채움)", 영지를 고르면 "이 영지 최소 가족 수(0 = 끔)"과 "이 영지만 따로 지정" 체크. 체크를 끄면 그 영지 키를 `regionTargets`에서 지우고 칸을 잠근다.
- "지금 바로 들일 가족 수"(1~20)와 "가족 추가" → `addFamilies`(영지를 골랐으면 그 영지).
- 설명 두 줄과 현재 상태 문구(패널과 같은 내용).

**상태**
- 패널의 상태 글과 같은 내용: 상태, heartbeat, inGame, appliedSeq/보낸 seq, bridgeError, [기능], [명령 결과], [네이티브].
- [오버레이] 항목: 버전(빌드 날짜), 토글 키 선택(Insert, Home, End, F7, F8, F9), 글자 배율(80~150%, 10% 단위. 바꾸면 다음 프레임부터 적용).

**로그** (2026-10-02 사용자 요청)
- UE4SS 로그(`<UE4SS 폴더>/UE4SS.log`. `bridge`의 세 단계 위)의 끝부분을 보여 준다. 작업 스레드가 1초마다 새로 붙은 부분만 읽어 줄로 나누고 가장 새로운 1,000줄을 기억한다(처음에는 파일 끝의 256KB부터).
- 줄: 시각(`HH:MM:SS`)과 글. 모드가 남긴 줄(`[Lua] [MLToybox] …`)은 그 머리를 떼고 보인다. 오류 줄(모드의 `ERROR …`, UE4SS의 `Error: …`)은 빨간색, 모드와 무관한 줄은 흐리게.
- "MLToybox 줄만"(처음에 켜져 있다), 검색(시각과 글에서 찾는다), "새 줄 따라가기"(줄이 늘면 맨 아래로), "복사"(보이는 줄을 클립보드로).
- 모드가 남기는 줄: 시작(네이티브·오버레이 DLL 올린 결과), 게임 상태 전환, 기능이 켜지고 꺼진 것(`feature X: on`, `feature X: off (이유)`), 명령 결과(`command X: ok`, `ERROR command X: 이유`), 기능 실행 오류.

### 2.5 입력
- 토글 키는 창 프로시저에서 `WM_KEYDOWN`(반복 입력 제외)으로 가로채고 게임에 넘기지 않는다. 입력 칸에 커서가 있어도 토글 키는 토글로 동작한다.
- 창이 열려 있을 때: 직전 프레임에 ImGui가 마우스를 원하면(`WantCaptureMouse`) 마우스 메시지를, 키보드를 원하면(`WantCaptureKeyboard`) 키·문자 메시지를 게임에 넘기지 않는다.
- 창이 닫혀 있으면 토글 키 말고는 아무것도 가로채지 않는다.
- 창을 닫을 때 ImGui와 백엔드에 남은 눌린 버튼·키를 비운다(버튼을 누른 채 닫으면 백엔드가 잡은 마우스가 풀리지 않는다. 마우스 옆 버튼 포함).
- 창을 열 때 커서가 게임 창 안에 있으면 그 위치를 ImGui에 알려 준다. 닫혀 있는 동안의 마우스 이동은 ImGui에 넣지 않으므로, 알려 주지 않으면 마우스를 움직이기 전의 첫 클릭이 창 위에서도 게임으로 간다.
- 한글 입력(용병단 이름)은 지원 대상이다. 시스템 입력기(IME)는 쓰지 않고 오버레이가 직접 조합한다.
  - 까닭(2026-10-02 실측, `analysis/findings.md`): 게임 창은 IMM 입력기가 꺼져 있고 언리얼이 자기 TSF 문서 관리자를 그 창에 묶어 둔다. 창의 IMM 컨텍스트를 다시 붙여도 TSF의 포커스는 게임의 문서에 남아, 사용자가 한글을 칠 수 없었다. 게임의 TSF 포커스를 가로채는 것은 게임 자체의 글자 입력을 건드리는 일이라 하지 않는다.
  - 오버레이는 게임 창의 IME를 건드리지 않는다(꺼진 채로 둔다). 영문 글쇠는 `WM_CHAR`로 그대로 온다.
  - 글자 칸에는 한/영 상태가 있다. 한글 모드에서는 영문 글쇠를 두벌식으로 조합한다(겹모음, 겹받침, 윗글쇠의 쌍자음, 받침이 다음 글자의 첫소리로 넘어가는 것, 지우기 글쇠로 자모 하나 지우기). 조합 중인 글자는 글자 칸 안에 바로 보인다.
  - 한/영은 한/영 글쇠(`VK_HANGUL`)나 이름 칸 옆의 단추("A"/"한")로 바꾼다. 글자 칸에 커서가 있는 동안의 한/영 글쇠는 게임에 넘기지 않는다.
  - 커서를 옮기거나, 글이 밖에서 바뀌거나(붙여넣기), 글자 칸을 떠나거나, 한/영을 바꾸면 조합을 끝낸다. 붙여넣은 글자는 조합하지 않는다.
  - 한자 변환과 다른 언어의 입력기는 지원하지 않는다. 그런 글자는 붙여넣기로 넣는다.
  - 조합기와 글자 칸 연결은 단위 테스트한다(글자 칸은 그래픽 없이 ImGui 프레임으로 돌린다). 게임에서의 실제 타자는 사용자가 확인했다(2026-10-02).
- 복사(Ctrl+C, Ctrl+X)와 붙여넣기(Ctrl+V) 모두 화면 스레드는 Windows 클립보드를 만지지 않는다(3.3). 복사한 글은 적어 두면 작업 스레드가 클립보드에 쓴다(클립보드가 바쁘면 2초 동안 다시 한다). 붙여넣을 글은 글자 칸에 커서가 있는 동안 작업 스레드가 시스템 클립보드가 바뀔 때마다 읽어 두고, 화면 스레드는 그 글을 쓴다.

### 2.6 메인 메뉴와 연결이 끊긴 때
- 창은 열린다. 설정(체크박스, 목표값, 용병단 정의)은 바꿀 수 있고 저장된다.
- 게임 상태가 필요한 부분(자원 현재 값, 영지 목록, 분대 목록, 상태 문구)은 비워 두고 "게임에 들어가면 표시됩니다"를 보인다.
- 일회성 버튼은 누를 수 없게 한다(명령은 60초가 지나면 모드가 버리므로 미리 보내는 것은 의미가 없다).

### 3.3 스레드
| 스레드 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 화면 출력(게임의 RHI 스레드, `Present` 후킹 안) | ImGui 프레임, 화면 코드, 그리기 | 파일 읽기·쓰기 |
| 창(게임 스레드, 창 프로시저 후킹 안) | 토글 키 처리, 창이 열려 있으면 ImGui에 입력 전달, 게임에 넘길지 결정, 글자 칸에 커서가 있는 동안 한/영 글쇠 세기 | 화면 그리기, 파일 읽기·쓰기 |
| 작업(오버레이 DLL이 만든 스레드) | 후킹 설치, `status.json` 읽기(1초), `catalog.json` 읽기(바뀌었을 때), `UE4SS.log` 이어 읽기(1초), `control.json` 저장(변경 뒤 0.2초 안), 밖에서 바뀐 설정 다시 읽기, `overlay.json`·`overlay_status.json` 쓰기, 시스템 클립보드 읽기·쓰기 | 화면 그리기, ImGui 호출 |

- 나눠 쓰는 상태(`app`)는 잠금 하나(`App::mutex`)로 보호한다: 설정 문서, 최신 상태 문서(불변 사본의 공유 포인터), 변경 표시, 보낼 명령, 마지막으로 보낸 `seq`, 저장 오류. 저장·다시 읽기의 순서 규칙은 코어의 `session`에 두어 단위 테스트한다.
- 화면 스레드는 프레임마다 잠금을 잡고 상태 사본 포인터를 받고, 설정을 고칠 때만 문서를 바꾼다. 작업 스레드는 저장할 때 문서의 사본을 만든 뒤 잠금을 풀고 파일에 쓴다.
- ImGui는 스레드 안전하지 않다. 스파이크는 창 프로시저에서 ImGui 입력 함수를 잠금 없이 불러 경합 가능성이 있었다. ImGui를 부르는 곳(화면 스레드의 프레임, 창 스레드의 입력 전달)은 모두 잠금 하나(`imguiMutex`) 아래에서 부른다. 잠금 순서는 `imguiMutex` 다음 `App::mutex`다.
  - `imguiMutex`는 재진입 잠금이다. 창 프로시저는 같은 스레드에서 다시 불린다(백엔드가 부르는 `ReleaseCapture`가 `WM_CAPTURECHANGED`를 보낸다). 재진입이 안 되는 잠금이면 그 안에서 예외가 나고, 창 프로시저 밖으로 나간 예외는 게임을 끝낸다(사전 검증에서 실제로 튕겼다. `analysis/findings.md` "게임 안 오버레이 창 — 계획 코드 사전 검증").
  - 다른 스레드가 `SendMessage`로 보낸 메시지는 ImGui에 넘기지 않는다(보낸 쪽이 잠금을 쥐고 기다리면 서로 멈춘다). 마우스·키 입력은 큐로 오는 메시지라 해당하지 않는다.
  - 시스템 IME 는 쓰지 않는다. ImGui의 기본 IME 처리를 끄고(`IMGUI_DISABLE_WIN32_DEFAULT_IME_FUNCTIONS`) IME 콜백도 비워 둔다. 화면 스레드는 글자 칸에 커서가 있는지(`wantText`)만 원자 값으로 적고, 창 스레드는 그동안 한/영 글쇠를 누른 횟수를 센다(`hangulKeys`). 조합은 화면 스레드가 프레임 안에서 한다(2.5).
  - 화면 스레드는 Windows 클립보드를 읽지도 쓰지도 않는다. ImGui의 기본 처리는 잠금을 쥔 채 클립보드를 연다. 쓸 때는 비우면서, 읽을 때는 글을 그때 만들어 주는 프로그램이면, Windows가 클립보드를 가진 창(게임 창일 수 있다)에 메시지를 보내고 답을 기다린다. 그 창의 스레드가 `imguiMutex`를 기다리고 있으면 서로 멈춘다. 그래서 화면 스레드는 `App`에 적어 둔 글만 읽고 쓰고, 시스템 클립보드는 작업 스레드가 잠금 밖에서 다룬다(`ui/clipboard_sync`). 실제로 멈추는 것을 재현해 보지는 않았다.
  - 입력을 큐에 넣었다가 화면 스레드에서 넘기는 방식은 쓰지 않는다. `ImGui_ImplWin32_WndProcHandler`가 부르는 Win32의 마우스 캡처·키 상태 함수는 창을 가진 스레드에서 불러야 하기 때문이다.
- 게임에 넘길지는 창 스레드가 바로 정해야 하므로, 화면 스레드가 프레임마다 갱신하는 원자 값(`wantMouse`, `wantKeyboard`, `visible`)을 본다. 한 프레임 늦은 값이다.
- 구조적 예외가 나면 C++ 소멸자가 불리지 않아 잠금이 풀리지 않는다. 화면 스레드와 창 스레드는 잠금을 쥐고 있는지 적어 두고, 예외 처리기가 직접 푼다.

### 3.4 코어의 규칙 (패널 `Panel.Core`와 같은 동작)
- **설정 문서**: nlohmann `ordered_json`을 그대로 들고, 아는 키는 접근 함수로 읽고 쓴다. 모르는 키는 건드리지 않아 보존된다. 키가 없으면 패널의 기본값을 쓴다(예: `build.instantBuild = true`, `mercenaries.refund = true`, `population.multiplier = 2`, `resources.intervalSec = 2`).
- **옛 설정 옮기기**: `features.lord`가 없고 `resources.targets`에 `Treasury`·`Influence`가 있으면 영주 설정으로 옮긴다(패널의 `LordControl.MigrateFrom`).
- **저장**: `version = 1`, `seq = max(파일의 seq, 메모리의 seq) + 1`. 들여쓰기한 UTF-8로 `control.json.tmp`에 쓰고 이름을 바꾼다. 이름 바꾸기가 실패하면 50ms 간격으로 5번까지 다시 한다.
- **명령**: `id`는 32자리 16진수, `issuedAt`은 UTC 초. 보낸 명령은 모드가 실행했다고 알릴 때까지(`status.json`의 `commands`에 그 `id`가 보일 때까지) 저장할 때마다 `commands`에 다시 싣는다. 60초가 지난 명령은 뺀다(모드도 버린다).
  - 패널처럼 "한 번 저장하고 바로 비우면" 안 된다. 모드는 1초마다 읽고 오버레이는 바뀔 때마다 저장하므로, 모드가 읽기 전에 나간 다음 저장이 명령을 지운다("지금 설정"을 연달아 누르면 앞의 것이 사라진다. 코드 리뷰에서 찾아 2026-10-01에 고쳤다). 모드는 같은 `id`를 한 번만 실행하므로 여러 번 실어도 된다.
- **상태 문서**: Lua의 JSON 인코더는 빈 표를 `{}`가 아니라 `[]`로 쓴다. 객체 자리에 온 배열은 빈 객체로 읽는다.
- **연결 상태**: 패널의 `BridgeClient.Evaluate`와 같다(`heartbeat` 5초).
- **용병단 검증**(패널 `MercCompanyRules`, 모드 `merc_plan.validate`와 같은 규칙):
  - 이름: 앞뒤 공백을 뗀 뒤 1~40자. 길이는 코드 포인트로 센다(모드와 같다. 패널은 UTF-16 단위였다).
  - 순정 이름 11개와 겹치지 않는다(대소문자 무시). 다른 용병단과 겹치지 않는다(대소문자 무시, 자기 자신 제외).
  - 분대 1~10개. 고용비 0 이상.
  - "사용"은 최대 3개.
  - 깃발: 순정 이름 11개 가운데 하나 또는 없음. 모르는 이름은 없음으로 바꾼다.
  - 도착 영지 선택지: "내 첫 영지", 내 영지들, 저장된 키 가운데 목록에 없는 것.
- **병종 목록**: 패널의 `UnitCatalog`와 같은 13종과 한글 이름.

## 4. 데이터

### 4.1 브리지
- `control.json`, `status.json`: 모양을 바꾸지 않는다.
- 패널과 함께 쓸 때: 작업 스레드가 1초마다 `control.json`의 `seq`를 읽는다. 오버레이가 마지막으로 읽거나 쓴 값보다 크고 저장 대기 중인 변경이 없으면 다시 읽는다. 저장 대기 중인 변경이 있으면 오버레이의 문서를 저장한다(나중에 쓴 쪽이 이긴다).

### 4.2 `bridge/overlay.json` (오버레이가 읽고 쓴다)
```json
{ "toggleKey": "Insert", "scale": 1.0, "window": { "x": 80, "y": 80, "w": 640, "h": 720 }, "startOpen": false, "devTab": null }
```
- `toggleKey`: `Insert`, `Home`, `End`, `F7`, `F8`, `F9` 가운데 하나. 모르는 값이면 `Insert`.
- `scale`: 0.8~1.5. 범위를 벗어나면 가까운 끝값.
- `startOpen`, `devTab`: 개발·검증용. `startOpen`이 참이면 열린 채로 시작하고, `devTab`에 탭 이름을 주면 그 탭을 연다(마우스 없이 창 캡처로 화면을 확인하기 위한 것). 화면에서는 고칠 수 없다.
- `resourceColumns`: 자원 표의 열 너비(자원, 분류, 현재, 목표). 표 너비에 대한 백분율 넷이다. 사용자가 열 경계를 끌었을 때만 적힌다. 없거나 수가 넷이 아니거나 0 이하의 값이 있으면 기본 너비(30, 26, 16, 28)를 쓴다.
- `inputLog`: 개발·검증용. 참이면 창이 열려 있는 동안의 글쇠·문자·IME 메시지를 `bridge/overlay_input.log`에 덧붙인다(입력 문제를 사용자의 실제 타자로 잴 때 쓴다). 꺼져 있으면 파일에 적지 않는다.
- 파일이 없거나 깨졌으면 기본값을 쓴다.
- 게임이 켜져 있는 동안 이 파일을 밖에서 고치면 작업 스레드가 1초 안에 다시 읽는다(저장 대기 중인 오버레이 쪽 변경이 없을 때). 게임을 다시 켜지 않고 `devTab`을 바꿔 가며 화면을 확인하기 위한 것이다.

### 4.3 `bridge/overlay_status.json` (오버레이가 쓴다, 1초마다)
```json
{ "heartbeat": 1790000000, "state": "ready", "reason": null, "visible": false, "frames": 12345, "font": "malgun" }
```
- `state`: `starting`(후킹 설치 중), `waiting`(큐를 찾는 중), `ready`(그릴 수 있음), `disabled`(포기함).
- `reason`: `disabled`일 때의 이유(5절).

### 4.4 `status.json`의 `overlay` (Lua가 합친다)
```json
"overlay": { "loaded": true, "error": null, "state": "ready", "reason": null, "stale": false }
```
- `loaded`·`error`: Lua가 DLL을 올린 결과. `config.overlay`가 거짓이면 `loaded = false, error = "disabled in config"`.
- 나머지는 `overlay_status.json`에서 가져온다(`native.status`와 같은 방식. `heartbeat`가 5초 넘게 지나면 `stale = true`). DLL을 올리지 못했으면 이 파일을 보지 않는다(지난 실행의 파일이 남아 있을 수 있다).

### 4.5 Lua 변경
- `config.lua`: `overlay = true`.
- `core/native.lua`: 파일 이름을 받아 올리는 함수와 `overlay_status.json`을 읽는 함수를 더한다.
- `main.lua`: 네이티브 DLL 다음에 오버레이 DLL을 올리고, 상태에 `overlay`를 넣는다.
- `main.lua`: DLL을 올리기 전에 `bridge/catalog.json`을 쓴다(4.6). 기능이 켜지고 꺼질 때(`registry.onChange`)와 명령을 처리했을 때(`commands`의 알림 함수) 로그에 한 줄을 남긴다.
- `features/resources_catalog.lua`: 품목마다 묶음 번호(`sub`, `EItemSubcategory`)와 한글 이름(`name`)을 두고, 영지 창의 순서로 놓는다. `describe()`가 이름 표를 만든다.

### 4.6 `bridge/catalog.json` (모드가 시작할 때 한 번 쓴다)
```json
{ "version": 1, "resources": [
  { "id": "RegionalWealth", "name": "지역 자산", "category": "영지" },
  { "id": "Timber", "name": "목재", "category": "건설", "group": "목재 작업물" } ] }
```
- 자원 79줄(지역 자산와 78종). 순서는 게임의 영지 창 순서이고, 오버레이는 이 순서를 "분류" 정렬에 쓴다.
- 바뀌지 않는 값이라 1초마다 쓰는 `status.json`에 싣지 않는다. 오버레이의 작업 스레드는 파일이 바뀌었을 때만 읽는다. 읽은 것이 비어 있으면 다음 회차에 다시 읽는다.
- 이름의 출처: 게임의 영지 창(사용자 캡처)과 번역 표 `DT_Translation_Items`의 `ko_KR`(`tools/lab/translations.lua`). `analysis/findings.md` "자원 이름과 번역 표".

## 5. 안전장치

### 5.1 끄는 방법
- `config.lua`의 `overlay = false`: Lua가 DLL을 올리지 않는다.
- `native/mltoybox_overlay.dll`을 지운다: Lua는 "not deployed"로 보고하고 계속한다.

### 5.2 그리지 않고 물러나는 경우
어느 경우든 게임과 기존 기능은 계속 돈다. 이유는 `overlay_status.json`의 `reason`에 적는다.

| 경우 | 동작 | `reason` |
|---|---|---|
| 가상 함수 표를 얻지 못함, 후킹 생성·활성화 실패 | 후킹하지 않는다 | `hook setup failed: …` |
| `Present` 스레드의 직접 큐를 20초 안에 찾지 못함 | 그 세션에서 그리지 않는다 | `present queue not found` |
| ImGui·DX12 객체 초기화 실패 | 그리지 않는다 | `init failed: …` |
| `GetDeviceRemovedReason()`이 `S_OK`가 아님 | 그 세션에서 다시 그리지 않는다 | `device removed 0x…` |
| 프레임 실행 중 C++ 예외 또는 구조적 예외(접근 위반 등) | 잡아서 오버레이를 끈다 | `frame exception …` |
| 창 프로시저에서 ImGui에 입력을 넘기는 중 C++ 예외 또는 구조적 예외 | 잡아서 오버레이를 끈다. 창 프로시저 밖으로 예외를 내보내지 않는다 | `input exception …` |

- 큐 선택: `ExecuteCommandLists` 후킹에서 직접(DIRECT) 큐마다 마지막으로 실행한 스레드를 기록한다. `Present` 후킹에서 지금 스레드와 같은 스레드의 큐를 고른다. 스파이크에서 직접 큐가 둘이었고, 다른 큐로 그리면 GPU 크래시가 났다.
- 그리는 대상: 스왑체인의 `OutputWindow`가 게임 메인 창(프로세스의 보이는 최상위 창 가운데 가장 큰 것)일 때만 그린다.
- 백버퍼 참조는 프레임 사이에 들고 있지 않는다(그릴 때 얻고 그 프레임 안에서 놓는다). 참조가 남아 있으면 게임의 `ResizeBuffers`가 실패하는데, 오버레이가 스스로 꺼진 뒤에는 놓아 줄 기회가 없다(코드 리뷰에서 찾아 테스트로 재현하고 고쳤다). `ResizeBuffers` 뒤 백버퍼 개수나 형식이 달라졌으면 명령 할당자와 ImGui 장치 객체를 다시 만든다.
- 명령 할당자는 GPU가 그 할당자의 지난 명령을 끝낸 뒤에만 다시 쓴다(펜스로 확인). 쓸 것이 없으면 할당자를 늘리고(최대 8개), 그래도 없으면 그 프레임은 그리지 않는다.
- `disabled`가 되면 창 프로시저 후킹은 토글 키를 포함해 아무것도 가로채지 않는다.

### 5.3 그 밖
- DLL은 프로세스가 끝날 때까지 고정한다(`pinModuleContaining`). 후킹과 창 프로시저를 되돌리지 않는다.
- 창 프로시저는 이전 프로시저를 `CallWindowProcW`로 이어 부른다(다른 프로그램의 후킹과 공존).
- `control.json` 저장 실패: 변경 표시를 유지하고 1초 뒤 다시 시도한다. 상태 줄에 "● 저장 실패". `overlay.json` 저장이 실패해도 다음 회차에 다시 쓴다.
- 읽을 수 없는 `control.json`(손으로 고치다 문법을 틀린 경우)으로 시작하면 기본값으로 뜬다. 저장은 읽을 수 없는 파일을 사본 없이 덮지 않는다: 저장할 때마다 파일을 보고, 읽을 수 없으면 `control.json.bak`으로 사본을 남긴 뒤에 덮는다. 사본을 못 남기면 저장하지 않는다(상태 줄 "● 저장 실패", 1초 뒤 다시). 게임 중에 파일이 밖에서 깨진 경우에도 같다. 파일이 없는 경우와 구별한다.
- 저장은 잘못된 UTF-8이 섞여 있어도 예외를 던지지 않는다(그 글자를 대체 문자로 쓴다). 작업 스레드의 한 회차가 예외로 끊기면 그 회차만 건너뛰고 횟수를 [상태] 탭에 보인다.
- `control.json`, `status.json`, `overlay.json`은 삭제 공유로 읽는다(모드나 패널이 파일을 지우고 다시 쓰는 것을 막지 않는다).
- 화면 후킹은 게임 코드의 주소가 아니라 DXGI·D3D12의 가상 함수 표에 건다. 게임이 업데이트돼도 주소를 다시 찾지 않는다.

### 5.4 확인하지 못한 조건
- 프레임 생성(FSR·DLSS FG)을 켠 상태. 화면 출력 경로가 달라질 수 있다. 5.2의 규칙으로 튕기지 않게 하되, 오버레이가 뜨는지는 구현 뒤 확인한다.
- HDR 출력, 다중 모니터 사이 이동, 전체 화면 전용 모드(`FullscreenMode=0`).
- Steam 오버레이 등 다른 오버레이와 함께 켠 상태(스파이크 때 Steam은 켜져 있었지만 따로 확인하지 않았다).

| 탭 8개의 화면 | `devTab`을 바꿔 가며 캡처. 문구·값이 `control.json`/`status.json`과 맞는지 |
| 토글 | 키 메시지를 보내고 `overlay_status.json`의 `visible` |
| 상태 줄 | 메뉴, 게임 안, 적용 대기 |
| 패널과 공유 | `control.json`을 밖에서 고치면 1~2초 안에 화면 값이 바뀜(캡처) |
| 해상도 변경 | 스파이크와 같은 방법 |
| 안전장치 | `config.overlay = false`일 때 DLL이 올라가지 않음. DLL을 지웠을 때 모드가 계속 동작 |
| 상태 합치기 | `status.json`의 `overlay` |

### 7.5 사용자 확인 항목
마우스 입력은 게임 창이 앞에 있어야 해서 자동으로 확인할 수 없다(스파이크에서 확인). 계획 A의 탭(영주, 건설, 업그레이드, 상태)에 대한 항목은 2026-10-01에 사용자가 확인했다("이상 없음"). 계획 B의 항목은 2026-10-02에 확인했다: 한글 입력이 되지 않았고 "재구성"을 여러 번 누르면 누른 만큼 분대가 생겼다. 그 밖은 정상이었다. 두 가지를 고친 뒤 같은 날 사용자가 다시 확인했다("이상 없음"). 리뷰에서 미룬 항목을 고친 뒤의 붙여넣기·복사, 용병 표의 줄 누르기, 다시 연 직후의 첫 클릭도 같은 날 확인했다.
- 탭마다 체크·숫자 입력·목록 선택이 즉시 반영되는지(상태 줄이 "적용 대기 중" → "적용됨").
- 자원 표 편집과 "모두 이 값으로".
- 용병단 등록, 고치기, 삭제, "사용" 체크(네 번째가 막히는지, 체크를 끄면 고용 창에서 카드가 빠지는지), 깃발.
- 한글 이름 입력(한/영 글쇠와 단추로 바꾸기, 받침·겹모음·쌍자음, 지우기 글쇠, 이름 칸을 벗어난 뒤 게임 단축키), 복사와 붙여넣기.
- 창 위의 클릭·휠·키 입력이 게임에 새지 않는지, 창 밖에서는 게임이 평소대로인지.
- 프레임 생성을 켰을 때(쓰는 경우).

## 8. 구현 순서
단계마다 게임에서 돌아가는 상태로 끝낸다. 구현 계획은 둘로 나눈다: 계획 A가 1~3단계, 계획 B가 4~7단계다. 계획 A가 끝나면 오버레이에 탭 4개(영주, 건설, 업그레이드, 상태)가 있고 나머지 탭은 패널로 설정한다. 계획 B는 4단계에 앞서 계획 A의 최종 리뷰에서 미룬 안전 항목(입력 비우기, 창 다시 걸기, 큐 고르기, 깨진 설정 파일의 사본, 작업 스레드 보호)과 글자 입력 기반(IME, 클립보드)을 먼저 넣는다. 계획 A 안에서는 단위 테스트를 먼저 쓸 수 있도록 코어(2단계)를 기반(1단계)의 DLL보다 먼저 만든다.

1. **기반**: 라이브러리 추가, 오버레이 DLL 골격(후킹, 빈 창, 토글, 입력, 안전장치, 상태 파일), Lua에서 올리기와 `config.overlay`, 배포 도구, `capture-game.ps1`.
2. **코어**: 설정·상태 문서, 브리지, 명령, 규칙, 테스트와 호환 견본. 작업 스레드와 `app` 상태, 상태 줄.
3. **간단한 탭**: 건설, 업그레이드, 영주, 상태(오버레이 설정 포함).
4. **군사, 인구**.
5. **자원**.
6. **용병**.
7. **문서와 검증**: README(오버레이가 기본 사용법, 패널은 비상용), CHANGELOG, findings, 게임 안 검증, `develop` 병합.
